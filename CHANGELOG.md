# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- Initial .NET 10 Minimal API solution in `andes-mailer-api/`, targeting SQL Server 2025. It has no mail features yet; it sets up the foundation for them: `/health/live` and `/health/ready` endpoints, Problem Details responses for every error, an OpenAPI reference in Development, and soft-delete and audit stamping for future entities.
- Initial Angular 22 workspace in `andes-mailer-ui/`. It has no mail features yet; it sets up the foundation for them: a feature-first `src/app` layout (`core`, `features`, `shared`) with path aliases and ESLint rules that enforce the layer boundaries, Bootstrap 5.3 compiled from Sass with the Andes palette in light and dark themes, a landing page, and a dev proxy that forwards `/api/**` to the API at `https://localhost:7093`. `@ngrx/signals` is installed and ready for the first store.
- Microsoft Entra sign-in for the API and the UI. Signed-out users go straight to Entra with no login screen (a failed sign-in lands on a `/login-failed` page), and the API accepts only JWT bearer tokens that carry the `access_as_user` scope. Every endpoint now requires that scope unless it opts out with `.AllowAnonymous()` (health checks, and OpenAPI and Scalar in Development). `GET /api/users/me` returns the signed-in user, and the home page shows the name. Behavior change: an anonymous request to an unknown API route now returns 401 instead of 404. Both apps currently share an app registration with `enterprise-gpt`, and there is no sign-out yet; see [docs/authentication.md](docs/authentication.md).
- Access-token renewal in the UI, so a session left open for hours does not stay broken. Tokens renew on demand through MSAL: a request that finds the token within MSAL's 5-minute window of expiry gets a fresh one first. There is no background timer, no renewal when you return to the tab or the connection comes back, and no retry of a 401 from `/api/`; a 401 or 403 reaches the caller as it is. When Entra needs you, the redirect to Entra reloads the page. The same happens after 24 hours, when Entra's refresh token for a single-page app expires and the browser blocks the silent fallback; see [docs/authentication.md](docs/authentication.md#token-renewal).
- User management in the API. `/api/users` can now list users (paginated), get one, add one by email, rename one, and deactivate one. Adding a user looks the account up in Microsoft Graph, so only the email is needed, and adding a deactivated user again reactivates them. Writes are guarded by permissions (`CreateUser`, `ModifyUser`, `DeactivateUser`) that users get through roles (`Administrator`, `TeamAdministrator`), checked on every request and answered with a 403 when missing. Stale edits and self-deactivation return 409. This adds the first database tables and migration (`Core.User`, `Core.UserRole`, and the `Core.Ref` role and permission tables), which seeds `rorro.irg@gmail.com` as the first administrator; apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. There are no endpoints to grant or revoke roles yet, so roles change through SQL, and a reactivated user starts with none. The Team permissions are seeded but nothing checks them. See [docs/users-and-permissions.md](docs/users-and-permissions.md).
- Draft emails with attachments in the API. `/api/emails` creates, lists, reads, updates, and deletes the signed-in user's drafts; a draft is visible only to its sender (anyone else gets 404), edits use the row `version` to catch conflicts, and the HTML body is sanitized to the formatting the compose editor produces. Recipients (To, Cc, Bcc) are matched to directory accounts through Microsoft Graph, and external addresses are kept as plain text. `POST /api/emails/{emailId}/attachments` accepts a PDF, DOCX, PPTX, PNG, JPEG, GIF, or WebP file (checked by extension and leading bytes; 25 MB per file and per email), answers 202, and uploads it to Azure Blob Storage in the background, retrying a storage or database fault for about a minute (`AttachmentUpload:MaxUploadAttempts`) before it marks the attachment `Failed`; poll the attachment until it is `Uploaded` or `Failed`, then download it from `/content`. Uploading and removing attachments need the new `CanAttachDocuments` permission, granted to `Administrator` and `TeamAdministrator`. Enums now travel by name in JSON. This adds tables and a migration (`Core.Email`, `Core.EmailRecipient`, `Core.EmailAttachment`, and their `Core.Ref` lookups); apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. The API now requires `BlobStorage:ConnectionString` (use `UseDevelopmentStorage=true` with Azurite locally), and `/health/ready` also checks blob storage. The upload pipeline assumes a single API instance. There is no UI, sending, or inline-image support yet. See [docs/emails-and-attachments.md](docs/emails-and-attachments.md).
- Teams in the API. A team is a group that composes emails together and sends from one shared directory mailbox, its service account, which the API verifies in Microsoft Graph and allows only one team to use, even when two requests race with different addresses of one mailbox (the loser gets 409). `/api/teams` lists, reads, creates, updates, and deactivates teams: only an `Administrator` writes (new permissions `CreateTeam`, `ModifyTeam`, `DeactivateTeam`), and `GET /api/teams` lists every team for an `Administrator` and otherwise only the caller's teams, each with the caller's `role`. `/api/teams/{teamId}/members` lists, reads, adds, re-roles, and removes members. Adding takes an email and a role, and adds the person as a user if they are not one yet (a user an `Administrator` deactivated, before or during the request, returns 409); removing a member leaves the user in their other teams, and demoting or removing a team's last `TeamAdministrator` returns 409. A new `TeamMember` role and the permissions `ViewTeam` and `ComposeTeamEmails` complete the grants. Team routes answer 404 to non-members and to deactivated teams, and 403 to members whose role lacks the permission. This adds `Core.Team` and `Core.TeamMember` and the migrations `AddTeams` and `AddTeamServiceAccountIdIndex`; apply them with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`, **after reading its data loss below**. There is no UI, no endpoint to reactivate a team, and sending is not implemented. See [docs/teams.md](docs/teams.md).
- Email templates in the API. A template is a team's reusable starting point for a draft: a name, a subject, a body, recipients, and attachments. `/api/teams/{teamId}/templates` lists (paginated, by name), reads, creates, updates, and deactivates templates, and `/api/teams/{teamId}/templates/{templateId}/attachments` uploads, reads, downloads, and removes their documents. Every team member can read templates; changing them needs the new permission `ManageTeamTemplates`, granted to `Administrator` and `TeamAdministrator` (a `TeamMember` gets a 403), and attachment changes also need `CanAttachDocuments`. A template name is unique among the team's active templates, so a duplicate name or a stale `version` returns 409, and a deactivated template frees its name. Template attachments follow the same file rules, the same 25 MB total, and the same background upload, retries, and startup recovery as email attachments; their blobs are stored in the `attachments` container as `templates/{templateId}/{attachmentId}`. `POST /api/teams/{teamId}/emails/from-template` takes `{ "templateId": "..." }` and lets any team member start a draft from a template: it copies the subject, body, recipients (looked up in the directory again), and every uploaded document, and returns 201. It returns 409 while a template attachment is still uploading and 404 when a document is missing from storage; the draft is independent afterwards, so later template changes never reach it. API contract change: `EmailDto` and `EmailSummaryDto` gain `templateId`, the template the draft was made from, or `null`. This adds `Core.EmailTemplate`, `Core.EmailTemplateRecipient`, `Core.EmailTemplateAttachment`, and a nullable `TemplateId` on `Core.Email` in the migration `AddEmailTemplates`, which deletes no data; apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. There is no UI for templates yet. See [docs/email-templates.md](docs/email-templates.md).
- Duplicate emails and email templates in the API. `POST /api/teams/{teamId}/emails/{id}/duplicate` (no body) copies a draft or a sent email into a new draft: the caller becomes the author, the `templateId` is kept, and the subject, body, and recipients are copied as stored, with no new directory lookup. `POST /api/teams/{teamId}/templates/{id}/duplicate` takes `{ "name": ... }` (a body is required, but `{}` is enough) and copies a template; without a name, the copy is called `"{Name} (copy)"`, then `"{Name} (copy 2)"` and so on, compared ignoring case, and a name that is given and already taken returns 409. Each copy gets its own copy of every `Uploaded` document (`Failed` ones are left out), stored as `{emailId}/{attachmentId}` or `templates/{templateId}/{attachmentId}`, so later changes to the source never reach it. Both routes return 201 with the new item, 404 when the source is missing, belongs to another team, or has a document gone from storage, and 409 while an attachment is still uploading. They need the new permission `DuplicateTeamEmails`, granted to `Administrator`, `TeamAdministrator`, and `TeamMember`; duplicating a template also needs `ManageTeamTemplates`, so a `TeamMember` gets a 403 there. This adds the migration `AddDuplicateTeamEmailsPermission`, which only seeds the permission and its grants; apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. There is no UI for duplicating yet. See [docs/emails-and-attachments.md](docs/emails-and-attachments.md#duplicate-an-email) and [docs/email-templates.md](docs/email-templates.md#duplicate-a-template).
- Duplicate-document check for attachments in the API. `POST /api/teams/{teamId}/emails/{emailId}/attachments` and `POST /api/teams/{teamId}/templates/{templateId}/attachments` now refuse a document whose content is already attached to the same email or template, whatever its file name: the response is 409 with "This document is already attached to the email as Q3 report.pdf." (or "...to the template as ..."), and nothing is staged or saved. Documents are compared by the SHA-256 of their bytes, so two different files with the same name are both accepted, and the same document on another email or template is accepted. `Failed` and removed attachments do not block a new upload; `Pending`, `Uploading`, and `Uploaded` ones do. Creating an email from a template, duplicating an email, and duplicating a template copy each document's hash, so later uploads to the copy are checked too. This adds the nullable `ContentHash` column to `Core.EmailAttachment` and `Core.EmailTemplateAttachment` in the migration `AddAttachmentContentHash`, which deletes no data; apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. There is no backfill, so documents attached before the migration are never matched. See [docs/emails-and-attachments.md](docs/emails-and-attachments.md#duplicate-documents) and [docs/email-templates.md](docs/email-templates.md#upgrading-the-addattachmentcontenthash-migration).
- Directory search in the API, for recipient autocomplete. `GET /api/users/directory?query=&limit=` finds people in the Entra directory by display name, first name, last name, or email address as someone types, and returns an array (not a page) of `{ id, firstName, lastName, fullName, email }` ordered by display name; `id` is the Entra object id, so it equals the app user's id when the person is a user, and `email` is the account's mail address or, when it has none, its sign-in name, in lowercase. `query` is 2 to 100 characters of letters, digits, spaces, and `. ' @ _ + -` (an `&` is rejected because of a known Graph `$search` bug) and `limit` is 1 to 25, default 10; anything else returns 400. Only an active user of the application can search: a deactivated user, or a token holder with no user row, gets 403, because the search reads through the API's app-only Graph access. Results are cached for 2 minutes and shared by every caller, so a new directory account can take about that long to appear. Each caller gets a token bucket partitioned by the `oid` claim (`RateLimiting:DirectorySearch`: `TokenLimit` 20, `TokensPerPeriod` 10, `ReplenishmentPeriod` `00:00:10`, validated when the API starts); over the limit, the API returns 429 Problem Details with a `Retry-After` header. It needs no new setup: it uses the existing `User.Read.All` application permission, and a Graph failure still returns 500. There is no UI for it yet. See [docs/users-and-permissions.md](docs/users-and-permissions.md#search-the-directory).
- Team contact groups in the API. A contact group is a named list of addresses that a team keeps in the app, so nobody needs an IT ticket for a distribution list. `/api/teams/{teamId}/contact-groups` lists (paginated, by name, with an optional `search` on the name), reads, creates, replaces, and deactivates groups. Every team member can list and read groups (permission `ComposeTeamEmails`); changing them needs the new permission `ManageTeamContactGroups`, granted to `Administrator` and `TeamAdministrator` (a `TeamMember` gets a 403), and callers outside the team get 404. A group holds 1 to 500 addresses, the same cap as an email's recipients so one group always fits in an email, in the order entered; any valid plain address is allowed, inside or outside the directory, with no duplicates (case and surrounding spaces are ignored), and directory addresses get a `userId` and `displayName` from Graph. The name (up to 100 characters) is unique among the team's active groups, so a duplicate name returns 409, and a deactivated group frees its name. `PUT` replaces the name, description, and members and needs the `version` you last read; a stale one returns 409, and changing only the members still bumps the version. To add a group to an email or template, the client reads the group and adds its addresses as ordinary recipients: the copy happens at that moment, later changes to the group never reach existing drafts, and deactivating a group leaves emails alone. The database keeps an audit trail: `[Core].[ContactGroup]` records `CreatedById` and `DeactivatedById`, and `[Core].[ContactGroupMember]` records `AddedById` and `RemovedById` with dates; removing an address soft-deletes its row and adding it again creates a new one, so the full membership history stays. Deactivating a team hides its groups. This adds those two tables, the permission, and its grants in the migration `AddContactGroups`, which deletes no data; apply it with `dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api`. There is no UI for contact groups yet. See [docs/contact-groups.md](docs/contact-groups.md) and [docs/emails-and-attachments.md](docs/emails-and-attachments.md#add-a-contact-groups-addresses).
- A root `README.md` with technology badges, an overview, local setup, build and test commands, and links to the docs.
- Sign in to the API from Scalar in Development. The OpenAPI document now declares an `Entra` OAuth2 scheme (authorization code flow, scope `api://<ClientId>/access_as_user`) and requires it on every operation that is not anonymous, and `/scalar` preselects it with PKCE, the UI's client id, and no client secret, so Authentication → Entra → Authorize lets Try It call protected endpoints instead of returning 401. The token is not stored between page loads. Register `https://localhost:7093/scalar` and `http://localhost:5145/scalar` as **single-page application** redirect URIs on the Entra app registration, or sign-in fails with `AADSTS50011`. Token validation is unchanged. See [docs/authentication.md](docs/authentication.md#calling-the-api-from-scalar).
- Telemetry for the API and the UI, in one Application Insights resource, so one trace id follows a click in the browser through the API, Microsoft Graph, SQL Server, and Blob Storage. The API uses the Microsoft OpenTelemetry Distro and exports only when `ApplicationInsights:ConnectionString` (user secrets locally) or the `APPLICATIONINSIGHTS_CONNECTION_STRING` variable that App Service sets is present; without one it still traces but sends nothing, so the tests export nothing. Traces are rate-limited to 5 a second (`ApplicationInsights:TracesPerSecond`), logs are never sampled, and `/health/*` is not traced or logged. Every request writes one log line (`HTTP {Method} {Path} responded {StatusCode} in {ElapsedMs} ms for user {UserId} ...`) with the final status, route, team, and trace id, and never a query string, header, or body; the request trace carries the caller as `enduser.id` (`user_AuthenticatedId`) and the team as `andes.team_id`. A Problem Details `traceId` already holds the trace id, so a user can hand you the id of a failed request. The dispatcher and the attachment uploader start `email.dispatch`, `email.deliver`, and `attachment.upload` activities, so a send or an upload is traceable by delivery or attachment id. The UI uses `@microsoft/applicationinsights-web` 3.4.6, loaded as a lazy chunk, and is on only when `public/config.json` has a `telemetry.connectionString`: it records a page view per route, tags each API call with the screen (`page`) and the operation (`apiOperation`), reports Angular errors, and records `UserSignedIn`; features report through the `Telemetry` service. People are identified by Entra object id only, never a name or an email address. Behavior change: the unhandled-exception error log now names the caller ("... for user {UserId}"). You create the Application Insights resource by hand (the repository has no infrastructure as code) and add its connection string to each environment; the UI stays off until you add the `telemetry` section. See [docs/telemetry/](docs/telemetry/README.md) for setup, the [API](docs/telemetry/api.md) and [UI](docs/telemetry/ui.md) details, and the [KQL queries](docs/telemetry/queries.md).

### Changed

- The UI now signs in through `@azure/msal-angular` 6.3.3, Microsoft's documented Angular pattern, and `@azure/msal-browser` 5.30.0. The Entra app registration and the `http://localhost:4200/auth` redirect URI are unchanged, and the API is untouched. See [docs/authentication.md](docs/authentication.md#how-sign-in-works).
- The API now holds a credential: it calls Microsoft Graph as itself, so the old "no client secret anywhere" rule no longer applies. Add the Graph application permission `User.Read.All` to the app registration with admin consent, and set `AzureAd:ClientSecret` in user secrets; the API does not check the credential at startup. See [docs/users-and-permissions.md](docs/users-and-permissions.md#microsoft-graph-setup) and [docs/authentication.md](docs/authentication.md#configuration).
- Breaking: emails belong to a team, not to the person who started them. The email routes moved from `/api/emails` to `/api/teams/{teamId}/emails`, and attachments from `/api/emails/{emailId}/attachments` to `/api/teams/{teamId}/emails/{emailId}/attachments`. Any member of the team can view, edit, attach to, and delete any of its drafts, and another team's draft is a 404. `SenderId` is now `AuthorId`, who started the draft, and `EmailDto` and `EmailSummaryDto` gain `authorId`. Update the UI's calls before it uses these routes. See [docs/emails-and-attachments.md](docs/emails-and-attachments.md).
- Breaking: roles are scoped. `Administrator` stays global, and `TeamAdministrator` is now held per team through `Core.TeamMember`, with check constraints that keep each role in its scope. `TeamAdministrator`'s grants change to `CreateTeamUser`, `ModifyTeamUser`, `DeactivateTeamUser`, `CanAttachDocuments`, `ViewTeam`, and `ComposeTeamEmails`, and `CreateTeamUser`, `ModifyTeamUser`, and `DeactivateTeamUser` now guard the member endpoints. See [docs/users-and-permissions.md](docs/users-and-permissions.md#roles-and-permissions).
- `DELETE /api/users/{id}` now also deactivates all of the user's team memberships.
- A new integration test fails the build if an API endpoint becomes reachable without a token: only `/health/live` and `/health/ready` may be anonymous, and an anonymous request to any `/api/` route must return 401. No behavior change; adding an anonymous route now means updating the test's allow-list. See [docs/authentication.md](docs/authentication.md#testing).
- The `AddTeams` migration **deletes every existing email, recipient, and attachment row** and cannot be undone: emails need a team, and earlier drafts have none. The documents stay in the `attachments` container; clear it by hand (in Azurite locally) if they matter. Back up a database you care about first. See [docs/teams.md](docs/teams.md#upgrading-the-addteams-migration).

### Removed

- The `/api/emails` routes, and the rule that only a draft's sender can see it. The `AddTeams` migration also deletes the global `TeamAdministrator` grants in `Core.UserRole`, so anyone who held that role must be added to a team instead.
