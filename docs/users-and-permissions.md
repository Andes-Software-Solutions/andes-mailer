# Users and permissions

Signing in with Entra proves who someone is; it says nothing about what they may do. The API keeps its own list of users, gives them roles, and checks a permission before each change to that list. This page covers the data model, the `/api/users` endpoints, how permission checks work, and the Microsoft Graph setup that adding a user needs. For how tokens are issued and validated, see [Authentication](authentication.md).

## How it fits together

- A **user** is an Entra account that someone with the `CreateUser` permission has added to Andes Mailer. The user's `Id` is the account's Entra object id (the `oid` claim in the token), so a token maps to a user row without a lookup table.
- A **role** is a named bundle of permissions. A user can hold several roles.
- A **permission** is one action the API checks before it runs.
- Adding a user takes only an email address. The API asks Microsoft Graph for the account that owns it and copies the id, name, and address, so nobody types an object id by hand.

Signing in does not create a user. A caller with a valid token whose `oid` has no active user row can still call the read endpoints, but holds no permissions.

## Data model

Application tables live in the `Core` schema. Fixed lookup data (roles, permissions, and which role grants which permission) lives in `Core.Ref`.

| Table | Holds |
| --- | --- |
| `[Core].[User]` | One row per user |
| `[Core].[UserRole]` | Which roles a user holds (`UserId`, `RoleId`) |
| `[Core.Ref].[Role]` | The roles |
| `[Core.Ref].[Permission]` | The permissions |
| `[Core.Ref].[RolePermission]` | Which permissions each role grants |

### `[Core].[User]`

| Column | Notes |
| --- | --- |
| `Id` | The Entra object id. Never generated by the database. |
| `FirstName`, `LastName` | Up to 100 characters each. `LastName` may be empty, because some directory accounts have no surname. |
| `Email` | Up to 256 characters, always stored in lowercase. Unique among active users only (a filtered unique index on rows where `DateDeactivated IS NULL`), so a deactivated row never blocks an address that someone else now holds. |
| `DateCreated`, `DateModified` | Stamped by the audit interceptor. `DateModified` is null until the first change. |
| `DateDeactivated` | Set when the user is deactivated (soft delete). Null for an active user. |
| `Version` | A SQL Server `rowversion`, used for optimistic concurrency. |

`FullName` is the first and last name joined by a space. It is computed in the DTO and has no column.

Queries on `User` and `UserRole` hide deactivated rows by default (the `Deactivation` query filter). A deactivated user disappears from the list, `GET /{id}` returns 404, and their roles grant nothing.

### Roles and permissions

| Role | Id | Permissions |
| --- | --- | --- |
| `Administrator` | 1 | All six |
| `TeamAdministrator` | 2 | `CreateTeamUser`, `ModifyTeamUser`, `DeactivateTeamUser` |

| Permission | Id | Checked by |
| --- | --- | --- |
| `CreateUser` | 1 | `POST /api/users` |
| `ModifyUser` | 2 | `PUT /api/users/{id}` |
| `DeactivateUser` | 3 | `DELETE /api/users/{id}` |
| `CreateTeamUser` | 4 | Nothing yet |
| `ModifyTeamUser` | 5 | Nothing yet |
| `DeactivateTeamUser` | 6 | Nothing yet |

The enums are `Roles` and `Permissions` in `Andes.Mailer.Common/Enums/`. The reference rows belong to the code, not to operators: they are seeded with `HasData`, so a change to a role's permissions ships as a new migration.

### Seed data

The first migration, `Andes.Mailer.Repository/Sql/Migrations/*_AddUsersRolesAndPermissions.cs`, creates these tables and inserts:

- the reference rows above (through `HasData`);
- a default administrator, `rorro.irg@gmail.com` (object id `4ee09cb0-d7e7-4be4-b82f-2674695eb9df`), and their `Administrator` role (through `InsertData` in the migration).

Without that first administrator nobody could hold `CreateUser`, so nobody could add the second user.

## Endpoints

All routes sit under `/api/users` and need a token with the `access_as_user` scope, like every other endpoint. Errors are Problem Details responses. The read endpoints need no permission; each write endpoint needs the permission shown.

| Method and route | Permission | Success |
| --- | --- | --- |
| `GET /api/users/me` | None | 200 with the caller's object id and name. Unchanged. |
| `GET /api/users` | None | 200 with one page of active users |
| `GET /api/users/{id}` | None | 200 with the user |
| `POST /api/users` | `CreateUser` | 201 with the user and a `Location` of `/api/users/{id}` |
| `PUT /api/users/{id}` | `ModifyUser` | 200 with the updated user |
| `DELETE /api/users/{id}` | `DeactivateUser` | 204 |

### The user object

```json
{
  "id": "4ee09cb0-d7e7-4be4-b82f-2674695eb9df",
  "firstName": "Rodrigo",
  "lastName": "Rojas",
  "fullName": "Rodrigo Rojas",
  "email": "rorro.irg@gmail.com",
  "dateCreated": "2026-11-03T05:37:13+00:00",
  "dateModified": null,
  "version": "AAAAAAAAB9E="
}
```

`version` is the base64 row version. Send it back unchanged when you update the user.

### List users

```http
GET /api/users?page=1&pageSize=25
```

| Parameter | Default | Range |
| --- | --- | --- |
| `page` | 1 | 1 to 21474836 |
| `pageSize` | 25 | 1 to 100 |

Users are ordered by last name, then first name. The response wraps the page:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 25,
  "totalCount": 0
}
```

A value outside the range returns a 400 validation problem. A page past the end returns an empty `items` array.

### Get a user

`GET /api/users/{id}` returns 404 when no active user has that id, including a deactivated one.

### Add a user

```http
POST /api/users
Content-Type: application/json

{ "email": "ana.perez@example.com" }
```

The API trims and lowercases the address, then looks the account up in Microsoft Graph by `mail` or `userPrincipalName`. It matches `mail` as well because an external (guest) account signs in under a name like `name_domain#EXT#@tenant`, so only `mail` holds the address people know. The name comes from the directory's `givenName` and `surname`. If an account has no `givenName`, the first name falls back to its display name, then to the part of the address before the `@`.

| Status | When |
| --- | --- |
| 201 | The user was added. |
| 400 | `email` is empty, longer than 256 characters, or not an email address. |
| 403 | The caller lacks `CreateUser`. |
| 404 | No directory account owns the address. |
| 409 | An active user already has the address, the directory account is already a user under a different address, or another request added the same user at the same moment. |

**Reactivation.** The key is the Entra object id, so adding a deactivated person again reuses their row instead of creating a second one. The API clears `DateDeactivated` and refreshes the name and address from the directory. The reactivated user starts with **no roles**, because deactivation revoked them; see [Known limitations](#known-limitations).

### Update a user

```http
PUT /api/users/4ee09cb0-d7e7-4be4-b82f-2674695eb9df
Content-Type: application/json

{ "firstName": "Rodrigo", "lastName": "Rojas", "version": "AAAAAAAAB9E=" }
```

Only the name changes; the email comes from the directory and cannot be edited here. The request carries the `version` you last read, and the update applies only if the row still has it. If anyone changed the user in between, the API returns 409 and you read the user again before retrying. Without this, two people editing at once would silently overwrite each other.

| Status | When |
| --- | --- |
| 200 | The name was saved. The response holds the new `version`. |
| 400 | `firstName` is empty or over 100 characters, `lastName` is missing or over 100 characters, or `version` is not an 8-byte base64 row version. |
| 403 | The caller lacks `ModifyUser`. |
| 404 | No active user has that id. |
| 409 | The `version` is stale. |

### Deactivate a user

`DELETE /api/users/{id}` soft-deletes the user: it stamps `DateDeactivated` and deletes the user's `UserRole` rows, in one save. The user row stays, so the history and the object id are preserved.

| Status | When |
| --- | --- |
| 204 | The user was deactivated. |
| 403 | The caller lacks `DeactivateUser`. |
| 404 | No active user has that id. |
| 409 | The caller is deactivating themselves, or the user changed during the operation. |

Self-deactivation is blocked so the last administrator cannot lock everyone out by accident.

## How permission checks work

`PermissionEndpointFilter` (`Andes.Mailer.Api/Filters/`) runs on each write endpoint, before request validation and the handler:

1. It reads the caller's `oid` claim. If the claim is missing or not a GUID, the request fails with 403.
2. It asks `IPermissionService` whether the user holds the endpoint's permission through any role (`UserRole` joined to `RolePermission`).
3. If not, it returns a 403 Problem Details response saying which permission is required.

Because the check runs on every request and reads the database, a role change takes effect on the caller's next call; there is nothing to wait out in the token. A deactivated or unknown user holds no permissions.

To protect a new endpoint, add `.AddEndpointFilter(new PermissionEndpointFilter(Permissions.X))` to it. Add a new permission as an enum value and a migration that seeds it and the role grants.

## Microsoft Graph setup

Adding a user calls Microsoft Graph with the API's own identity (an app-only call), not the signed-in user's. That is why the API now needs a credential, which [replaces the old "no client secret anywhere" rule](authentication.md#configuration).

### Once per environment: grant the permission

1. In the Entra admin center, open the app registration `b40defa0-5309-45c4-82fc-cb284010cc10`.
2. Under **API permissions**, add the Microsoft Graph **application** permission `User.Read.All`.
3. Choose **Grant admin consent**. Without consent, Graph returns 403 and `POST /api/users` fails with a 500.

### Local development: a client secret

Create a client secret under **Certificates & secrets** on the same registration, then store it in user secrets so it never reaches the repository:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<value>" --project Andes.Mailer.Api
```

Run it from `andes-mailer-api/`. `appsettings.sample.json` shows where `ClientSecret` sits, after `ClientId`. Never put the secret in `appsettings.json`.

## Apply the migration locally

From `andes-mailer-api/`, with `SqlDb:ConnectionString` set as described in `AGENTS.md`:

```bash
dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api
```

`--startup-project` is required because `dotnet ef` starts the host to build the `DbContext`. This creates the tables and inserts the seed data above. The API does not apply migrations when it starts, so run this again after pulling a new migration.

## Known limitations

- **No role management.** No endpoint grants or revokes roles. Until one exists, change `[Core].[UserRole]` with SQL. A reactivated user starts with no roles, so an administrator has to re-grant them the same way.
- **Team permissions do nothing yet.** Teams do not exist, so `CreateTeamUser`, `ModifyTeamUser`, and `DeactivateTeamUser` and the `TeamAdministrator` role are seeded, but no endpoint checks them.
- **Graph failures return 500.** A Graph outage, a missing consent, or a bad credential surfaces as a 500 from `POST /api/users`, not a specific error. The cause is in the API logs.
- **No UI.** The UI calls only `GET /api/users/me`; it has no screens for the other endpoints yet.
