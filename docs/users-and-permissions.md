# Users and permissions

Signing in with Entra proves who someone is; it says nothing about what they may do. The API keeps its own list of users, gives them roles, and checks a permission before each change to that list, to a team, and to its emails. This page covers the data model, the `/api/users` endpoints, how permission checks work, and the Microsoft Graph setup that adding a user needs. For how tokens are issued and validated, see [Authentication](authentication.md). For teams and their members, see [Teams](teams.md). For the endpoints that check `ComposeTeamEmails`, `CanAttachDocuments`, and `DuplicateTeamEmails` on emails, see [Emails and attachments](emails-and-attachments.md). For the ones that check `ManageTeamTemplates` and `DuplicateTeamEmails` on templates, see [Email templates](email-templates.md).

## How it fits together

- A **user** is an Entra account that someone with the `CreateUser` permission has added to Andes Mailer, or that a team administrator added to a team (which adds them as a user first). The user's `Id` is the account's Entra object id (the `oid` claim in the token), so a token maps to a user row without a lookup table.
- A **role** is a named bundle of permissions. Its **scope** says where it applies: `Administrator` applies across the application, while `TeamAdministrator` and `TeamMember` apply in one team. A user holds at most one global role, and one team role in each team they belong to.
- A **permission** is one action the API checks before it runs.
- Adding a user takes only an email address. The API asks Microsoft Graph for the account that owns it and copies the id, name, and address, so nobody types an object id by hand.

Signing in does not create a user. A caller with a valid token whose `oid` has no active user row can still call the read endpoints, but holds no permissions.

## Data model

Application tables live in the `Core` schema. Fixed lookup data (roles, permissions, and which role grants which permission) lives in `Core.Ref`.

| Table | Holds |
| --- | --- |
| `[Core].[User]` | One row per user |
| `[Core].[UserRole]` | Which **global** roles a user holds (`UserId`, `RoleId`). Only `Administrator` fits; a check constraint (`CK_UserRole_RoleId`) rejects team roles. |
| `[Core].[Team]`, `[Core].[TeamMember]` | Teams, and which **team** role each user holds in each. See [Teams](teams.md#data-model). |
| `[Core.Ref].[Role]` | The roles |
| `[Core.Ref].[Permission]` | The permissions |
| `[Core.Ref].[RolePermission]` | Which permissions each role grants |

### `[Core].[User]`

| Column | Notes |
| --- | --- |
| `Id` | The Entra object id. Never generated by the database. |
| `FirstName`, `LastName` | Up to 100 characters each. `LastName` may be empty, because some directory accounts have no surname. |
| `Email` | Up to 256 characters, always stored in lowercase. Unique among active users only (a filtered unique index on rows where `DateDeactivated IS NULL`), so a deactivated row never blocks an address that someone else now holds. |
| `DateCreated`, `DateModified` | Stamped by the audit interceptor. `DateModified` is null until the first change. |
| `DateDeactivated` | Set when the user is deactivated (soft delete). Null for an active user. |
| `Version` | A SQL Server `rowversion`, used for optimistic concurrency. |

`FullName` is the first and last name joined by a space. It is computed in the DTO and has no column.

Queries on `User` and `UserRole` hide deactivated rows by default (the `Deactivation` query filter). A deactivated user disappears from the list, `GET /{id}` returns 404, and their roles grant nothing. Their team memberships are deactivated with them; see [Deactivate a user](#deactivate-a-user).

### Roles and permissions

| Role | Id | Scope | Permissions |
| --- | --- | --- | --- |
| `Administrator` | 1 | Global | All fourteen. In a team, this includes its emails and templates. |
| `TeamAdministrator` | 2 | One team | `CreateTeamUser`, `ModifyTeamUser`, `DeactivateTeamUser`, `CanAttachDocuments`, `ViewTeam`, `ComposeTeamEmails`, `ManageTeamTemplates`, `DuplicateTeamEmails` |
| `TeamMember` | 3 | One team | `CanAttachDocuments`, `ViewTeam`, `ComposeTeamEmails`, `DuplicateTeamEmails` |

| Permission | Id | Checked by |
| --- | --- | --- |
| `CreateUser` | 1 | `POST /api/users` |
| `ModifyUser` | 2 | `PUT /api/users/{id}` |
| `DeactivateUser` | 3 | `DELETE /api/users/{id}` |
| `CreateTeamUser` | 4 | `POST /api/teams/{teamId}/members`: adding a member to a team |
| `ModifyTeamUser` | 5 | `PUT /api/teams/{teamId}/members/{userId}`: changing a member's role |
| `DeactivateTeamUser` | 6 | `DELETE /api/teams/{teamId}/members/{userId}`: removing a member |
| `CanAttachDocuments` | 7 | `POST` and `DELETE` on `/api/teams/{teamId}/emails/{emailId}/attachments` and on `/api/teams/{teamId}/templates/{templateId}/attachments`: uploading a document to a draft or a template and removing one |
| `CreateTeam` | 8 | `POST /api/teams` |
| `ModifyTeam` | 9 | `PUT /api/teams/{teamId}` |
| `DeactivateTeam` | 10 | `DELETE /api/teams/{teamId}` |
| `ViewTeam` | 11 | `GET /api/teams/{teamId}` and `GET` on `/api/teams/{teamId}/members` |
| `ComposeTeamEmails` | 12 | Every route under `/api/teams/{teamId}/emails`, including attachment reads and `POST .../emails/from-template`; and every route under `/api/teams/{teamId}/templates`, so every team member can read and use templates |
| `ManageTeamTemplates` | 13 | `POST`, `PUT`, and `DELETE` on `/api/teams/{teamId}/templates`, and `POST` and `DELETE` on `/api/teams/{teamId}/templates/{templateId}/attachments`: creating, changing, and deactivating a template and its documents. Each also needs `ComposeTeamEmails`, and the attachment routes `CanAttachDocuments` |
| `DuplicateTeamEmails` | 14 | `POST /api/teams/{teamId}/emails/{id}/duplicate` and `POST /api/teams/{teamId}/templates/{id}/duplicate`: copying an email into a new draft and a template into a new template. Both also need `ComposeTeamEmails`, and the template route `ManageTeamTemplates`, so a `TeamMember` can duplicate an email but not a template |

Team creation, editing, and deactivation (8 to 10) are held by `Administrator` only, so a team administrator can manage who is in their team but not the team itself. `ManageTeamTemplates` (13) is held by `Administrator` and `TeamAdministrator`: a `TeamMember` can read and use a team's templates but not change them, and gets a 403 on the write routes. `DuplicateTeamEmails` (14) is held by all three roles, but duplicating a template also needs `ManageTeamTemplates`, so only `Administrator` and `TeamAdministrator` can do it. `GET /api/teams` needs no permission; it lists the teams the caller belongs to, or every team for an `Administrator`.

The permissions that guard team routes are checked **in the team**: a `TeamMember` in Team A holds nothing in Team B. A user with no role and no team, such as one you just added or reactivated, can do nothing beyond the read endpoints of `/api/users` until someone adds them to a team. See [Teams](teams.md#how-team-access-is-checked) and [Emails and attachments](emails-and-attachments.md#attachments).

The enums are `Roles` and `Permissions` in `Andes.Mailer.Common/Enums/`, and `RoleScopes` in `Andes.Mailer.Common/Constants/Users/` lists which roles are global and which are team roles. The reference rows belong to the code, not to operators: they are seeded with `HasData`, so a change to a role's permissions ships as a new migration. The team grants arrive in the migration `*_AddTeams.cs`, `ManageTeamTemplates` and its grants in `*_AddEmailTemplates.cs`, and `DuplicateTeamEmails` and its grants in `*_AddDuplicateTeamEmailsPermission.cs`.

### Seed data

The first migration, `Andes.Mailer.Repository/Sql/Migrations/*_AddUsersRolesAndPermissions.cs`, creates these tables and inserts:

- the reference rows above (through `HasData`);
- a default administrator, `rorro.irg@gmail.com` (object id `4ee09cb0-d7e7-4be4-b82f-2674695eb9df`), and their `Administrator` role (through `InsertData` in the migration).

Without that first administrator nobody could hold `CreateUser`, so nobody could add the second user.

## Endpoints

All routes sit under `/api/users` and need a token with the `access_as_user` scope, like every other endpoint. Errors are Problem Details responses. The read endpoints need no permission; each write endpoint needs the permission shown.

| Method and route | Permission | Success |
| --- | --- | --- |
| `GET /api/users/me` | None | 200 with the caller's object id and name. Unchanged. |
| `GET /api/users` | None | 200 with one page of active users |
| `GET /api/users/{id}` | None | 200 with the user |
| `POST /api/users` | `CreateUser` | 201 with the user and a `Location` of `/api/users/{id}` |
| `PUT /api/users/{id}` | `ModifyUser` | 200 with the updated user |
| `DELETE /api/users/{id}` | `DeactivateUser` | 204 |

### The user object

```json
{
  "id": "4ee09cb0-d7e7-4be4-b82f-2674695eb9df",
  "firstName": "Rodrigo",
  "lastName": "Rojas",
  "fullName": "Rodrigo Rojas",
  "email": "rorro.irg@gmail.com",
  "dateCreated": "2026-11-03T05:37:13+00:00",
  "dateModified": null,
  "version": "AAAAAAAAB9E="
}
```

`version` is the base64 row version. Send it back unchanged when you update the user.

### List users

```http
GET /api/users?page=1&pageSize=25
```

| Parameter | Default | Range |
| --- | --- | --- |
| `page` | 1 | 1 to 21474836 |
| `pageSize` | 25 | 1 to 100 |

Users are ordered by last name, then first name. The response wraps the page:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 25,
  "totalCount": 0
}
```

A value outside the range returns a 400 validation problem. A page past the end returns an empty `items` array.

### Get a user

`GET /api/users/{id}` returns 404 when no active user has that id, including a deactivated one.

### Add a user

```http
POST /api/users
Content-Type: application/json

{ "email": "ana.perez@example.com" }
```

The API trims and lowercases the address, then looks the account up in Microsoft Graph by `mail` or `userPrincipalName`. It matches `mail` as well because an external (guest) account signs in under a name like `name_domain#EXT#@tenant`, so only `mail` holds the address people know. The name comes from the directory's `givenName` and `surname`. If an account has no `givenName`, the first name falls back to its display name, then to the part of the address before the `@`.

| Status | When |
| --- | --- |
| 201 | The user was added. |
| 400 | `email` is empty, longer than 256 characters, or not an email address. |
| 403 | The caller lacks `CreateUser`. |
| 404 | No directory account owns the address. |
| 409 | An active user already has the address, the directory account is already a user under a different address, or another request added the same user at the same moment. |

**Reactivation.** The key is the Entra object id, so adding a deactivated person again reuses their row instead of creating a second one. The API clears `DateDeactivated` and refreshes the name and address from the directory. The reactivated user starts with **no roles and no teams**, because deactivation revoked them; see [Known limitations](#known-limitations).

**Adding through a team.** A team administrator who [adds a member](teams.md#add-a-member) by email also adds the person as a user, with the same Graph lookup, and needs no `CreateUser`. That path never reactivates: it returns 409 for a deactivated user, so only someone with `CreateUser` can undo a deactivation.

### Update a user

```http
PUT /api/users/4ee09cb0-d7e7-4be4-b82f-2674695eb9df
Content-Type: application/json

{ "firstName": "Rodrigo", "lastName": "Rojas", "version": "AAAAAAAAB9E=" }
```

Only the name changes; the email comes from the directory and cannot be edited here. The request carries the `version` you last read, and the update applies only if the row still has it. If anyone changed the user in between, the API returns 409 and you read the user again before retrying. Without this, two people editing at once would silently overwrite each other.

| Status | When |
| --- | --- |
| 200 | The name was saved. The response holds the new `version`. |
| 400 | `firstName` is empty or over 100 characters, `lastName` is missing or over 100 characters, or `version` is not an 8-byte base64 row version. |
| 403 | The caller lacks `ModifyUser`. |
| 404 | No active user has that id. |
| 409 | The `version` is stale. |

### Deactivate a user

`DELETE /api/users/{id}` soft-deletes the user: it stamps `DateDeactivated`, deletes the user's `UserRole` rows, and deactivates all their `TeamMember` rows, in one save. That includes memberships in teams that are already deactivated, so reactivating a team later cannot bring back someone deactivated in the meantime. A membership added concurrently is swept too, so none outlives its user. The user row stays, so the history and the object id are preserved, and so do the emails they started (`authorId`).

| Status | When |
| --- | --- |
| 204 | The user was deactivated. |
| 403 | The caller lacks `DeactivateUser`. |
| 404 | No active user has that id. |
| 409 | The caller is deactivating themselves, or the user changed during the operation. |

Self-deactivation is blocked so the last administrator cannot lock everyone out by accident. Deactivating a user can leave a team without a team administrator; see [The last team administrator](teams.md#the-last-team-administrator).

## How permission checks work

There are two filters, one for each scope of role. Both run before request validation and the handler.

### Global permissions

`PermissionEndpointFilter` (`Andes.Mailer.Api/Filters/`) guards the `/api/users` writes and `POST`, `PUT`, and `DELETE` on `/api/teams`:

1. It reads the caller's `oid` claim. If the claim is missing or not a GUID, the request fails with 403.
2. It asks `IPermissionService` whether the user holds the endpoint's permission through a global role (`UserRole` joined to `RolePermission`).
3. If not, it returns a 403 Problem Details response saying which permission is required.

### Team permissions

`TeamPermissionEndpointFilter` guards every route under `/api/teams/{teamId}` except the three team writes above. It looks at the caller's membership in that team first, then at their global roles:

| Caller | Result |
| --- | --- |
| A member whose team role grants the permission, or a global role that grants it | Proceeds |
| A member whose team role does not grant it | 403 naming the permission |
| Not a member, with no global grant | 404, so the API never confirms a team exists |
| Any caller, when the team is missing or deactivated | 404, even for an `Administrator` |

[Teams](teams.md#how-team-access-is-checked) walks through the cases.

Both checks run on every request and read the database, so a role or membership change takes effect on the caller's next call; there is nothing to wait out in the token. A deactivated or unknown user holds no permissions.

To protect a new endpoint, add `.AddEndpointFilter(new PermissionEndpointFilter(Permissions.X))` to it, or `new TeamPermissionEndpointFilter(Permissions.X)` for a route under `/api/teams/{teamId:guid}`. Add a new permission as an enum value and a migration that seeds it and the role grants.

## Microsoft Graph setup

Adding a user calls Microsoft Graph with the API's own identity (an app-only call), not the signed-in user's. That is why the API now needs a credential, which [replaces the old "no client secret anywhere" rule](authentication.md#configuration).

### Once per environment: grant the permission

1. In the Entra admin center, open the app registration `b40defa0-5309-45c4-82fc-cb284010cc10`.
2. Under **API permissions**, add the Microsoft Graph **application** permission `User.Read.All`.
3. Choose **Grant admin consent**. Without consent, Graph returns 403 and `POST /api/users` fails with a 500.

### Local development: a client secret

Create a client secret under **Certificates & secrets** on the same registration, then store it in user secrets so it never reaches the repository:

```bash
dotnet user-secrets set "AzureAd:ClientSecret" "<value>" --project Andes.Mailer.Api
```

Run it from `andes-mailer-api/`. `appsettings.sample.json` shows where `ClientSecret` sits, after `ClientId`. Never put the secret in `appsettings.json`.

## Apply the migration locally

From `andes-mailer-api/`, with `SqlDb:ConnectionString` set as described in `AGENTS.md`:

```bash
dotnet ef database update --project Andes.Mailer.Repository --startup-project Andes.Mailer.Api
```

`--startup-project` is required because `dotnet ef` starts the host to build the `DbContext`. This creates the tables and inserts the seed data above. The API does not apply migrations when it starts, so run this again after pulling a new migration.

The `AddTeams` migration **deletes every existing email, recipient, and attachment row** and removes global `TeamAdministrator` grants. It cannot be undone; read [Upgrading](teams.md#upgrading-the-addteams-migration) before you apply it to a database you care about.

## Known limitations

- **No management of the global role.** No endpoint grants or revokes `Administrator`. Until one exists, change `[Core].[UserRole]` with SQL. Team roles are managed through [the member endpoints](teams.md#team-members). A reactivated user starts with no roles and no teams, so an administrator has to re-grant the global role the same way and add them to their teams again.
- **Graph failures return 500.** A Graph outage, a missing consent, or a bad credential surfaces as a 500 from `POST /api/users`, not a specific error. The cause is in the API logs.
- **No UI.** The UI calls only `GET /api/users/me`; it has no screens for the other endpoints yet.
